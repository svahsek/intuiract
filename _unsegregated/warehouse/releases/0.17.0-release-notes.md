# Release Notes

**Version**: 0.17.0
**Released**: 04 March 2026
**Release Type**: Minor
**Product**: Inji Verify (INJIVER)

## Release Summary

### Inji Verify 0.17.0 Adds CWT Credential Support and V2 Verification APIs

This release adds support for CBOR Web Token (CWT) credentials, including Claim 169 QR codes, alongside the existing SD-JWT and LDP credential formats. It also introduces V2 verification API endpoints that return structured, per-credential results.

Beyond new credential and API support, this release closes three security gaps (response header hardening, a reflected-XSS path, and an object-injection vector in the UI), fixes 17 defects across SVG rendering, VP verification, and UI accessibility, and migrates the verify-service runtime database to resolve an open-source license compliance issue.

**Key Benefits**:
- ✨ Adds CWT/Claim 169 credential verification alongside existing SD-JWT and LDP support
- ✨ New V2 API endpoints return structured, per-credential verification results
- ✨ Closes 3 security gaps: response header hardening, reflected XSS, object injection
- ✨ Resolves an open-source license compliance issue by migrating the runtime database from H2 to HSQLDB

## What's New

### New Features

#### CBOR Web Token (CWT) / Claim 169 Credential Support

Verify service, SDK, and UI can now verify COSE/CBOR-based (CWT) credentials, including Claim 169 QR codes, alongside existing SD-JWT and LDP formats.

- **Use Case**: Implementers integrating credentials issued in CWT format (e.g. Claim 169 age/attribute QR codes) can verify them through the same verification flow used for SD-JWT and LDP credentials, without format-specific integration work.
- **Key Capabilities**:
  - Automatic credential format detection across submission and verification flows
  - CWT claim extraction and exposure (iss, cnf, sub, aud, exp, nbf, iat, cti)
  - QR code scanning and decoding for Claim 169 CWT credentials in the SDK and UI
- **Documentation**: [Claim 169](https://github.com/inji/inji-verify/blob/v0.17.0/docs/Claim169.md)
- **Related Issues**: INJIVER-1366, INJIVER-1389, INJIVER-1529

#### V2 Verification API Endpoints

New V2 endpoints return structured verification results with per-credential checks, replacing the single pass/fail response of the V1 endpoints.

- **Use Case**: API consumers that need to know which specific credential in a presentation failed verification, and why, can call the V2 endpoints instead of parsing an aggregate V1 result.
- **Key Capabilities**:
  - `POST /v2/vc-verification` returns schema/signature/expiry/status checks per credential
  - `GET /v2/vp-results/{transactionId}` returns transactionId, allChecksSuccessful, and per-credential results including holder-proof checks
  - Optional claim inclusion and status-check filtering on request
  - SD-JWT and LDP claims exposed in V2 responses
- **Documentation**: [API Documentation (OpenAPI)](https://github.com/inji/inji-verify/blob/v0.17.0/docs/api-documentation-openapi.yaml)
- **Related Issues**: INJIVER-1488, INJIVER-1491, INJIVER-1533, INJIVER-1519

#### VP Submission Without Holder Proof

The verify-service and SDK now accept verifiable presentations submitted without a holder proof, controlled by an explicit acceptVPWithoutHolderProof flag.

- **Use Case**: Flows such as DataShare, where the wallet does not attach a holder proof to the VP, can now complete verification instead of being rejected outright.
- **Key Capabilities**:
  - acceptVPWithoutHolderProof flag on /vp-request and /vp-results
  - Same flag available in the SDK's OpenID4VP and QR code verification flows
  - Default behavior unchanged: holder proof is still required unless the flag is set
- **Documentation**: [API Documentation (OpenAPI)](https://github.com/inji/inji-verify/blob/v0.17.0/docs/api-documentation-openapi.yaml)
- **Related Issues**: INJIVER-1489

### Enhancements

#### SDK Package Migration to @injistack/react-inji-verify-sdk

The React SDK previously published as @mosip/react-inji-verify-sdk is deprecated in favor of @injistack/react-inji-verify-sdk, with an in-package deprecation banner and migration guide.

| Aspect | Details |
|--------|---------|
| **Previous Behavior** | Consumers installed and imported the SDK as @mosip/react-inji-verify-sdk. |
| **New Behavior** | Consumers should install @injistack/react-inji-verify-sdk; the old package name continues to work but displays a deprecation banner. |
| **User Impact** | No functional change until the old package is removed; import paths need to be updated to adopt the new package name. |
| **Migration Required** | Update package.json and import statements from @mosip/react-inji-verify-sdk to @injistack/react-inji-verify-sdk. No API changes are required beyond the package name. |

**Documentation**: [Inji Verify SDK - OpenID4VP](https://github.com/inji/inji-verify/blob/v0.17.0/docs/InjiVerifySDKOpenID4VP.md)

#### SDK Session State Handling

The SDK no longer persists QR verification session state via pathname/session storage, reducing the amount of verification-flow state kept in the browser.

| Aspect | Details |
|--------|---------|
| **Previous Behavior** | Verification session state, including a stored pathname, persisted across the QR verification flow. |
| **New Behavior** | Session state is streamlined and pathname storage has been removed from the verification workflow. |
| **User Impact** | No action required; behavior change is internal to the SDK's session handling. |

**Documentation**: [Inji Verify SDK - Scan and Upload](https://github.com/inji/inji-verify/blob/v0.17.0/docs/InjiVerifySDKScanAndUpload.md)

## ⚠️ Security Updates

**IMPORTANT**: Review security updates below before deploying.

### Hardened HTTP response security headers

**Severity**: 🟡 Medium
**Affected Versions**: 0.16.0
**Upgrade Recommended**: Yes

Verify service responses now set X-Frame-Options: SAMEORIGIN and X-Content-Type-Options: nosniff, and no longer send the legacy X-XSS-Protection header, which modern browsers ignore.

### Reflected XSS via error response path

**Severity**: 🔴 High
**Affected Versions**: 0.16.0
**Upgrade Recommended**: Yes

Error responses previously echoed the request path back to the client, creating a reflected cross-site scripting vector. Error responses no longer include the request path.

### Object injection vulnerability in verify-ui

**Severity**: 🟡 Medium
**Affected Versions**: 0.16.0
**Upgrade Recommended**: Yes

Dynamic property-key access in credential data processing and theme handling could be manipulated to access unintended object properties. Property-key access is now validated before use.

## Technical Improvements

### Infrastructure Updates

#### Migrated the verify-service runtime database from H2 to HSQLDB

Resolves an open-source license compliance issue with the previously embedded H2 database.

#### Upgraded verify-service base image from eclipse-temurin:21-jre-alpine to eclipse-temurin:25.0.1_8-jre-alpine

Moves the service onto a current, supported Java base image.

#### Upgraded react-router-dom from 6.22.3 to 6.30.3 in verify-ui

Keeps the UI's routing dependency current with upstream fixes.

#### Integrated an updated vc-verifier library release candidate (1.6.0-SNAPSHOT to 1.7.0-RC3)

Brings in upstream verification library fixes ahead of a stable release.
