Yes, exactly — the gap between the auto-generated and hand-written spec is entirely closeable through Swagger/OpenAPI annotations in the Java code. Here's what you can do:

---
Annotations that close the gap

1. Controller-level tagging — @Tag

Groups endpoints under named sections (like your YAML has "VP Request", "VC Verification", etc.):
@Tag(name = "VP Request", description = "APIs for Verifiable Presentation Authorization Request related operations")
@RestController
public class VPRequestController { ... }

2. Endpoint descriptions — @Operation

The biggest win. Adds summary, full description (supports markdown), and marks deprecated endpoints:
@Operation(
    summary = "Initiate a new VP Request",
    description = "## Description\nThis endpoint initiates a **Verifiable Presentation (VP) request**..."
)
@PostMapping("/vp-request")
public ResponseEntity<...> createVPRequest(...) { ... }

3. Response documentation — @ApiResponse / @ApiResponses

Documents every HTTP status code and what it means:
@ApiResponses({
    @ApiResponse(responseCode = "200", description = "VP Request created successfully"),
    @ApiResponse(responseCode = "400", description = "Invalid request body"),
    @ApiResponse(responseCode = "404", description = "Presentation definition not found")
})

4. Request/response model schemas — @Schema

Annotates DTOs/POJOs so the generated schema has field descriptions and examples:
public class VPRequestDto {
    @Schema(description = "Unique identifier for the presentation definition", example = "kyc-basic-v1")
    private String presentationDefinitionId;
}

5. Path/query parameter descriptions — @Parameter

public ResponseEntity<...> getResult(
    @Parameter(description = "The VP request transaction ID", required = true)
    @PathVariable String transactionId
) { ... }

6. Global metadata — already in OpenAPIConfig.java

You can also enrich the existing OpenAPIConfig bean with contact info, license, and servers — matching what the hand-written YAML has at the top:
return new OpenAPI()
    .info(new Info()
        .title("OpenID4VP Verifier API - Inji Verify")
        .version("1.0.2")
        .contact(new Contact().name("MOSIP").url("https://mosip.io").email("mosip.emailnotifier@gmail.com"))
        .license(new License().name("MPL-2.0").url("https://www.mozilla.org/en-US/MPL/2.0/")))
    .servers(List.of(new Server().url("https://injiverify.collab.mosip.net/v1/verify")));

---
What this means for your repo

All 7 controllers (VPRequestController, VCVerificationController, VPDefinitionController, etc.) currently have zero annotations beyond Spring MVC ones. Adding @Tag + @Operation + @ApiResponse to each, and @Schema to the DTOs, would make the runtime /v3/api-docs output match or exceed the hand-written YAML in quality.

The hand-written docs/api-documentation-openapi.yaml could then either be retired (truth lives in code) or generated from the running app (springdoc-openapi-maven-plugin can dump /v3/api-docs to a file at build time), keeping it in sync automatically.

---
Bottom line: Yes, code annotations are exactly the right approach. The entire hand-written YAML is expressible through @Tag, @Operation, @ApiResponse, @Schema, and @Parameter — all from the io.swagger.v3.oas.annotations package, which is already on your classpath via springdoc.
